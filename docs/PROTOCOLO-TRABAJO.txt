# PROTOCOLO ESTRICTO DE TRABAJO PARA MATHVOICE

A partir de este momento seguí ESTE ORDEN DE TRABAJO sin desviarte.

Este protocolo tiene prioridad sobre cualquier tendencia a agregar funcionalidades nuevas, refactorizar innecesariamente o volver a fases que ya fueron implementadas.

No quiero que trabajes simultáneamente en muchas áreas.

Terminá, verificá y cerrá cada bloque antes de avanzar.

---

# REGLA 1 — NO EMPEZAR DE NUEVO

Este proyecto YA tiene trabajo realizado.

No reconstruyas MathVoice desde cero.

No vuelvas a implementar una función que ya existe sin antes comprobar si realmente está rota.

Antes de modificar algo:

1. Inspeccioná lo existente.
2. Determiná si funciona.
3. Determiná qué problema tiene.
4. Corregí únicamente lo necesario.
5. Probalo.
6. Continuá.

La regla es:

INSPECCIONAR → CORREGIR → PROBAR → CERRAR → CONTINUAR.

Nunca:

REHACER → REHACER → REHACER.

# PASO 4 — CERRAR EL SISTEMA DE TECLADO PARA PERSONAS CIEGAS

Después de estabilizar la navegación base, terminar el sistema completo de teclado.

Este bloque es prioritario porque MathVoice está diseñado para una persona ciega.

Debe existir:

MODO ESCRITURA.

y:

MODO TECLADO MATEMÁTICO.

No mezclar ambos.

---

# PASO 4.1 — MODO ESCRITURA

En modo escritura:

Las teclas deben comportarse normalmente.

Debe ser posible escribir:

x^2 + 5*x - 3

sin activar comandos accidentalmente.

No interceptar letras y números mientras el usuario escribe en campos normales.

---

# PASO 4.2 — MODO TECLADO MATEMÁTICO

Crear un modo especializado donde teclas y combinaciones ejecuten funciones matemáticas.

Ejemplos:

R:
raíz.

S:
seno.

C:
coseno.

T:
tangente.

D:
derivada.

I:
integral.

F:
factorizar.

Etcétera.

Los comandos deben depender del contexto cuando corresponda.

Por ejemplo:

D dentro de cálculo puede significar derivada.

D dentro de matrices puede significar determinante.

La aplicación debe anunciar siempre el contexto actual.

---

# PASO 4.3 — ADMINISTRADOR CENTRAL DE ATAJOS

Todos los shortcuts deben administrarse desde un único sistema.

Por ejemplo:

KeyboardCommandManager.

No distribuir keydown listeners descontrolados por todos los componentes.

Cada comando debe conocer:

* Identificador.
* Nombre.
* Tecla.
* Modificadores.
* Categoría.
* Contexto.
* Acción.
* Mensaje hablado.
* Si puede personalizarse.

---

# PASO 4.4 — NO INTERFERIR CON EL LECTOR DE PANTALLA

* NVDA.
* JAWS.
* VoiceOver.
* Chrome.
* Edge.
* Firefox.
* Safari.
* Windows.
* macOS.

No capturar globalmente:

Insert.

Caps Lock.

Modificadores de VoiceOver.

Ni otros comandos reservados importantes.

No usar role="application" globalmente solo para capturar teclado.

---

# PASO 4.5 — DESCUBRIMIENTO DE ATAJOS

Una persona ciega NO debe necesitar memorizar los comandos antes de usar MathVoice.

Implementar:

“¿Qué hace esta tecla?”

El usuario presiona una tecla.

MathVoice anuncia su función.

Sin ejecutarla.

# PASO 4.6 — MODO ENTRENAMIENTO

Crear:

“Practicar teclado”.

En este modo ninguna tecla ejecuta operaciones.

Solo se explica qué haría.

Ejemplo:

Usuario pulsa D.

MathVoice:

“D. Derivada.”

Usuario pulsa Shift+D.

MathVoice:

“Shift D. Derivada de orden superior.”
